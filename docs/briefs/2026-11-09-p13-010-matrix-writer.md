# P13-010 — the V2 matrix writer (build handoff)

## Summary (STAR)

**Situation.** `plinking_duck` is Teague's DuckDB extension that reads and writes PLINK genetics
filesets (`.pgen`/`.pvar`/`.psam`) in SQL. Its `COPY … (FORMAT pfile)` writer can shard a cohort along
ONE axis: `shard_by '<col>'` (variants, shipped) or `shard_samples {label:[iids],…}` (samples, merged
as PR #85). The two are mutually exclusive — the combined call is rejected on purpose.

**Task.** Build that follow-on: a single `COPY … (FORMAT pfile, shard_by '<vcol>', shard_samples {…})`
that shards BOTH axes into a `pfile_catalog: 2` **matrix** — M variant-blocks × N sample-blocks, so M
`.pvar` + N `.psam` + M·N `.pgen` + the catalog. The v2 matrix reader (`pfile_catalog_matrix.cpp`,
`ParseMatrixCatalog`/`BuildCells`) and ATTACH (`TYPE pfile_catalog`) already parse this; nothing writes
it yet.

**Action.** Execute the committed plan test-first. The design and plan are on this branch
(`feature/P13-010-matrix-writer`, off `origin/main` 576034b). The grid is the shipped variant roll with
P13-007's sample fan-out as its inner loop — reuse, don't re-invent.

**Result.** Nothing built. Design + plan are written and approved; one design fork is already decided
(below). Your job is the build → review → PR.

## Decided up front (do not re-litigate)

- **Variant-axis keys = B, compound (Teague's call).** Emit a `CHROM` enum key (`over:"CHROM"` only
  when `<vcol>` is `CHROM`, case-insensitive) PLUS a `CHUNK` `ordinal_interval`-over-`POS` key carrying
  per-block `bounds:{min,max}` from the roller's `pos_min`/`pos_max`. This gives CHROM **and** POS
  cell-skip (≥ the v1 variant-sharded catalog) at ~zero cost. Blocks form, not the short form.
- **Dense grid, no `holes`** — every variant row reaches every sample-block.
- **Reuse, don't re-implement:** `ParseSampleShards`, `PgenRowGenotypes`/`GenotypeCalls`/
  `PgenAppendCallRange`, `CheckSampleShardResources` (guard on N, the concurrent writer count),
  `WritePsamFromIids`, `PvarWriteChunk`, the variant roller's block-boundary + `pos_min/max` logic.

## What is already measured (verbatim — do not rediscover)

- The v2 reader prunes cells on BOTH CHROM (`ContigKey`, enum `over=="CHROM"`,
  `pfile_catalog_matrix.cpp:586`) and POS (`ordinal_interval`-over-`POS` bounds, `:580`). That is WHY
  fork B (compound keys) is chosen — enum-only would drop POS cell-skip.
- Enum `over` is read from JSON (`:62`); emit `"over":"CHROM"` on the CHROM key for `ContigKey` to
  resolve.
